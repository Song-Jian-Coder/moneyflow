# Brainstorming — 需求梳理与设计讨论

本技能是任何创意工作的入口。在动手写代码之前，通过结构化对话将模糊需求转化为明确设计方案。

## 核心原则

> 先讨论，后设计，再动手。未经人类批准设计方案，不写任何生产代码。

## Iron Law — 铁律

> **HARD-GATE：必须在人类批准设计方案后才能写代码。没有例外。**

## 三路分类系统

收到需求后，先判断其规模，选择对应流程：

| 类型 | 适用场景 | 仪式感 | 流程 |
|------|----------|--------|------|
| **Spike（探针）** | 快速验证技术可行性 | 低 | 简短讨论 → 直接验证 |
| **Bounded（有界）** | 明确范围的功能开发 | 中 | 需求讨论 → 设计方案 → 确认 |
| **Architectural（架构级）** | 影响深远的系统变更 | 高 | 多轮讨论 → 分步设计 → 逐段确认 |

## Process — 核心流程

### 1. 需求分析

- 仔细阅读用户需求
- 识别模糊点和隐含假设
- 列出需要澄清的问题

### 2. 主动提问

- 向用户提出具体问题，消除歧义
- 问题应聚焦于：边界条件、异常处理、接口风格、性能要求
- 不要一次提太多问题，分批提出

### 3. 设计方案

- 基于确认的需求，提出技术方案
- 包含：架构选择、关键接口、数据流、模块划分
- 分段展示，每段获得用户确认

### 4. 人类批准

- 汇总完整设计方案
- 明确请求用户批准
- **获得批准前，不写任何生产代码**

## Red Flags — 识别跳过讨论的信号

| 想法 | 现实 |
|------|------|
| "需求已经很清楚了，直接写吧" | 需求总有隐含假设需要确认 |
| "这只是个小改动" | 小改动的范围也需要对齐 |
| "用户会告诉我要什么的" | 主动提问比被动等待更高效 |
| "我已经做过类似的了" | 每次上下文不同，需要重新确认 |

## Common Rationalizations — 常见借口

| 借口 | 现实 |
|------|------|
| "讨论太花时间了" | 返工更花时间 |
| "先写个原型再说" | 原型经常变成生产代码 |
| "用户不懂技术，问了也白问" | 用户懂业务，你懂技术，两者都需要 |

## Verification Checklist

- [ ] 是否已判断任务规模（Spike/Bounded/Architectural）？
- [ ] 是否已识别并澄清了模糊点？
- [ ] 是否已提出设计方案并获得用户批准？
- [ ] 设计方案是否包含：架构、接口、数据流、模块划分？
- [ ] 是否在获得批准前避免了写生产代码？
