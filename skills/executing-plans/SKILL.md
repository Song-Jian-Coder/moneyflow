# Executing Plans — 计划执行

本技能负责按计划逐一执行任务。核心要求：按顺序执行、每任务完成后立即验证、设置检查点防止上下文丢失。

## 核心原则

> 严格执行计划，不跳步、不合并、不"顺便"做计划外的事。遇到计划偏差时暂停并更新计划。

## Iron Law — 铁律

> **一次只执行一个任务。完成一个，验证一个，再进入下一个。**

## Process — 核心流程

### 1. 准备阶段

- 确认计划文件已就绪（tasks.md 或等效文档）
- 确认当前工作分支正确
- 阅读即将执行的任务，确认理解

### 2. 执行任务

对每个任务执行以下步骤：

```
读取任务描述
├─ 确认依赖任务已完成
├─ 阅读涉及文件，理解当前状态
├─ 按具体操作逐步执行
│   └─ 内部强制调用 test-driven-development 技能
├─ 运行验证方式
│   ├─ 通过 → 标记任务完成，进入下一个
│   └─ 失败 → 在当前任务内修复，不带着问题往下走
└─ 更新任务状态
```

### 3. 检查点机制

每完成 3-5 个任务，设置一个检查点：

- 运行全量测试，确认无回归
- 检查已完成任务与计划是否一致
- 记录进度，防止上下文压缩丢失状态

### 4. 偏差处理

当发现计划需要调整时：

- **小偏差**（不影响整体架构）：更新计划文档，继续执行
- **大偏差**（影响多个模块或架构）：暂停执行，回到 brainstorming 重新讨论

## 进度追踪格式

```markdown
## 执行进度

- [x] Task 1: 实现 JWT token 生成 — 完成
- [x] Task 2: 实现 token 验证中间件 — 完成
- [ ] Task 3: 实现登录 API — 进行中
- [ ] Task 4: 编写集成测试 — 待执行
```

## Red Flags — 识别偏离计划的信号

| 想法 | 现实 |
|------|------|
| "这个任务太简单了，和下一个合并吧" | 合并后无法独立验证 |
| "先跳过这个任务，后面再回来" | 后面的任务可能依赖它 |
| "顺便把这个文件也重构了吧" | 计划外的改动是 bug 的温床 |
| "测试太多了，少跑几个" | 每个任务的验证都必须完整执行 |

## Verification Checklist

- [ ] 是否按顺序逐个执行任务？
- [ ] 每个任务完成后是否运行了验证？
- [ ] 是否每 3-5 个任务设置了检查点？
- [ ] 遇到偏差时是否更新了计划文档？
- [ ] 是否避免了计划外的"顺便"改动？
