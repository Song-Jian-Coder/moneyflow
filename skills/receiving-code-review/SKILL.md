# Receiving Code Review — 接收审查反馈

本技能定义如何专业地接收和处理代码审查反馈，确保每条意见都得到认真对待。

## 核心原则

> 审查反馈是质量提升的机会，不是对个人能力的质疑。每条反馈都必须被认真处理。

## Iron Law — 铁律

> **不忽视任何审查意见。即使不同意，也必须明确回应理由。**

## Process — 核心流程

### 1. 接收反馈

- 完整阅读所有审查意见
- 不要急于辩解或反驳
- 先理解审查者的关注点

### 2. 分类处理

将反馈分为三类：

| 类型 | 处理方式 |
|------|----------|
| **必须修复** | 逻辑错误、安全漏洞、缺失测试 → 立即修复 |
| **建议改进** | 代码风格、命名优化、性能改进 → 评估后决定是否采纳 |
| **需要讨论** | 设计分歧、方案选择 → 回到 brainstorming 讨论 |

### 3. 执行修复

- 按优先级处理"必须修复"项
- 每项修复后运行测试确认
- 修复完成后标记状态

### 4. 回应反馈

对每条审查意见给出明确回应：

```markdown
- [x] "这里缺少空值检查" → 已修复，添加了空值检查（commit abc123）
- [x] "建议用 Map 替代数组查找" → 已采纳，性能从 O(n) 降到 O(1)
- [ ] "这里应该用策略模式" → 不同意，原因是 [具体理由]，建议保持现状
```

### 5. 重审（如需要）

- 修复完成后，请求审查者重新检查
- 提供修复的具体位置和方式

## Red Flags — 识别不良处理方式的信号

| 想法 | 现实 |
|------|------|
| "审查者不懂这个模块" | 即使不懂，也可能是文档写得不够清楚 |
| "这个改动不影响功能" | 代码质量也是功能的一部分 |
| "太多意见了，先合并再说" | 带着问题合并只会让问题更大 |
| "他上次也犯同样的错" | 聚焦当前问题，不翻旧账 |

## Verification Checklist

- [ ] 是否已完整阅读所有审查意见？
- [ ] 是否已对每条意见分类（必须修复/建议改进/需要讨论）？
- [ ] "必须修复"项是否已全部修复并验证？
- [ ] 是否已对每条意见给出了明确回应？
- [ ] 修复后是否已请求重审？
