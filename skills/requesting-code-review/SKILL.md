# Requesting Code Review — 发起代码审查

本技能定义如何发起一次结构化的代码审查，确保变更在合并前经过充分检查。

## 核心原则

> 代码审查不是形式主义的过场，而是质量保障的最后一道防线。每次审查都必须有明确的审查范围和检查维度。

## Iron Law — 铁律

> **没有经过代码审查的变更，不能标记为完成。**

## When to Use — 使用时机

- 一个或多个任务执行完毕
- 一个功能分支开发完成，准备合并
- OpenSpec 变更的 apply 阶段完成
- 定期审查已有代码的质量

## Process — 核心流程

### 1. 准备审查包

整理以下信息供审查者使用：

```markdown
## 代码审查请求

**变更范围：** [简述本次变更的内容]
**关联任务：** [对应的 tasks.md 任务编号]
**变更文件列表：**
- `file1.ts` — 修改说明
- `file2.ts` — 新增说明

**审查重点：**
- [ ] 功能是否符合设计规格
- [ ] 测试是否充分覆盖
- [ ] 代码是否符合项目规范
```

### 2. 自审清单

在请求他人审查前，先完成自审：

- [ ] 所有测试是否通过？
- [ ] 是否有未使用的代码或导入？
- [ ] 命名是否清晰、一致？
- [ ] 是否有硬编码的魔法数字或字符串？
- [ ] 错误处理是否完善？
- [ ] 是否有安全风险（注入、XSS 等）？

### 3. 审查维度

审查应覆盖以下维度：

| 维度 | 检查内容 |
|------|----------|
| **功能正确性** | 是否符合设计规格和任务要求 |
| **测试覆盖** | 是否有充分的单元测试和集成测试 |
| **代码质量** | 命名、结构、复杂度、可读性 |
| **安全性** | 输入校验、注入防护、权限控制 |
| **性能** | 是否有明显的性能问题 |
| **一致性** | 是否与项目现有代码风格一致 |

### 4. 处理审查反馈

- 收到反馈后，使用 `receiving-code-review` 技能处理
- 不要忽视任何审查意见
- 有分歧时回到设计规格确认

## Verification Checklist

- [ ] 是否已完成自审清单？
- [ ] 是否已整理变更范围和审查重点？
- [ ] 所有测试是否已通过？
- [ ] 是否已确认变更符合设计规格？
