# Systematic Debugging — 系统化调试

本技能强制执行 4 阶段调试流程，杜绝"猜一下改一改"的临时起意式调试。

## 核心原则

> 先定位根因，再实施修复。没有根因调查，就不能修改代码。

## Iron Law — 铁律

> **不允许在未找到根因的情况下实施修复。猜测不是调试。**

## 四阶段流程

```
Phase 1: Root Cause Investigation（根因调查）
    ↓
Phase 2: Pattern Analysis（模式分析）
    ↓
Phase 3: Hypothesis & Testing（假设验证）
    ↓
Phase 4: Implementation（实施修复）
```

### Phase 1: Root Cause Investigation — 根因调查

**目标：** 确认问题能稳定复现，收集证据。

1. **复现问题**
   - 记录触发条件（输入、环境、状态）
   - 确认是必现还是偶现
   - 无法复现的 bug 无法验证修复

2. **收集证据**
   - 错误日志、堆栈跟踪
   - 最近的代码变更（git log/diff）
   - 环境差异（版本、配置、数据）

3. **划定范围**
   - 哪个模块/文件出了问题？
   - 什么时候开始出的？（git bisect）
   - 影响范围有多大？

### Phase 2: Pattern Analysis — 模式分析

**目标：** 根据证据分析问题模式。

- 是否与最近的变更有关？
- 是否是已知的常见问题模式？（空指针、竞态、内存泄漏等）
- 是否有类似的已解决问题可以参考？

### Phase 3: Hypothesis & Testing — 假设验证

**目标：** 形成假设并最小化验证。

1. 列出可能的根因（至少 2 个假设）
2. 对每个假设设计最小化验证实验
3. 逐一验证，排除错误假设
4. 确认根因

### Phase 4: Implementation — 实施修复

**目标：** 针对确认的根因实施最小化修复。

1. 编写复现测试（TDD：先写失败测试）
2. 实施修复（只改根因相关的代码）
3. 确认测试通过
4. 运行全量测试，确认无回归
5. 检查是否有类似问题需要一并处理

## Red Flags — 识别非系统化调试的信号

| 想法 | 现实 |
|------|------|
| "我猜是这里的问题" | 猜测不是调试，需要证据 |
| "先改改试试看" | 试错法效率极低 |
| "错误信息说是 X 行的问题" | 错误信息指向的未必是根因 |
| "上次也是这样修的" | 相同症状可能有不同根因 |

## 修复范围控制

| 情况 | 做法 |
|------|------|
| 根因明确，修复简单 | 直接修复，写测试 |
| 根因明确，修复复杂 | 拆解修复步骤，逐步验证 |
| 根因不明确 | 回到 Phase 1，不要跳到 Phase 4 |
| 发现多个根因 | 分别记录，按优先级逐个修复 |

## Verification Checklist

- [ ] 是否已稳定复现问题？
- [ ] 是否已收集了充分的证据（日志、堆栈、变更记录）？
- [ ] 是否已列出至少 2 个假设并逐一验证？
- [ ] 是否已确认根因（而非仅处理症状）？
- [ ] 修复后是否编写了回归测试？
- [ ] 是否运行了全量测试确认无回归？
