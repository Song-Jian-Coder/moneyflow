# Test-Driven Development — 测试驱动开发

本技能强制执行 TDD 的 RED-GREEN-REFACTOR 循环。这是 Superpowers 中最核心的纪律执行技能。

## 核心原则

> 先写失败的测试，再写最少的代码让它通过，最后重构。没有例外。

## Iron Law — 铁律

> **NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST. 没有失败的测试，就不能写生产代码。**

违反字面意思就是违反精神。如果 AI 在写测试之前就写了代码，必须删除代码，从头来过。

## RED-GREEN-REFACTOR 循环

```
┌──────────────────────────────────────────┐
│  RED      写一个刚好失败的测试             │
│           ↓                              │
│  GREEN    写刚好够用的代码让测试通过        │
│           ↓                              │
│  REFACTOR 清理代码，保持测试绿色            │
│           ↓                              │
│           回到 RED，开始下一个测试          │
└──────────────────────────────────────────┘
```

### RED — 写失败测试

- 写一个描述预期行为的测试用例
- 运行测试，确认它**失败**
- 如果测试通过了，说明你不需要写新代码

### GREEN — 写最少代码通过

- 只写让当前失败测试通过的最少代码
- 不多写、不预判、不"顺便"实现其他功能
- 代码可以丑陋，只要测试通过

### REFACTOR — 重构

- 在测试保护下优化代码结构
- 消除重复、改善命名、提取公共逻辑
- 重构后必须再次运行测试，确认仍然通过

## Red Flags — 识别跳过 TDD 的信号

| 想法 | 现实 |
|------|------|
| "这只是个小改动" | 大小不改变规则 |
| "我可以之后再补测试" | 你不会的 |
| "这次先写代码，测试后面补" | 无数研究证明相反更有效 |
| "测试会让代码变复杂" | 没有测试的代码才是真正的复杂 |
| "这个函数太简单了，不需要测试" | 简单的函数也可能有边界情况 |
| "用户很着急" | 仓促导致更多 bug，反而更慢 |

## Common Rationalizations — 常见借口

| 借口 | 现实 |
|------|------|
| "这次不一样" | 每次都一样 |
| "先写代码再写测试效率更高" | 短期可能，长期一定更慢 |
| "我是在做探索性编程" | 探索完了还是要先写测试 |
| "测试框架还没配好" | 先配测试框架，再写代码 |
| "这是配置改动，不需要测试" | 配置也可能出错，也需要验证 |

## 特殊场景处理

### 修复 Bug

1. 先写一个能复现 bug 的测试（RED）
2. 确认测试失败（证明 bug 存在）
3. 修复 bug（GREEN）
4. 确认测试通过（bug 已修复）
5. 重构（如果需要）

### 重构已有代码

1. 先为现有行为编写测试（确保有安全网）
2. 确认所有测试通过
3. 开始重构，每步都运行测试
4. 确认重构后所有测试仍然通过

## Verification Checklist

- [ ] 是否在写生产代码前先写了失败测试？
- [ ] 是否只写了让测试通过的最少代码？
- [ ] 是否在测试保护下进行了重构？
- [ ] 重构后是否再次运行了所有测试？
- [ ] 是否避免了"先写代码后补测试"？
