# Verification Before Completion — 完成前验证

本技能是交付前的最后一道质量门。在标记任何工作为"完成"之前，必须提供证据证明工作确实已完成且质量合格。

## 核心原则

> 声称完成不等于真的完成。用证据说话，不用声明说话。

## Iron Law — 铁律

> **没有验证证据，不能标记工作为完成。"我觉得做完了"不是证据。**

## Process — 核心流程

### 1. 规格合规检查

对照设计规格 / 任务描述，逐项确认：

```markdown
## 规格合规检查

| 规格要求 | 状态 | 证据 |
|----------|------|------|
| 实现 XX 功能 | ✅ | 测试 test_xx 通过 |
| 支持 XX 边界情况 | ✅ | 测试 test_xx_edge 通过 |
| 错误处理 XX 场景 | ❌ | 遗漏了 XX 场景的处理 |
```

### 2. 质量检查

| 检查项 | 验证方式 |
|--------|----------|
| 所有测试通过 | 运行全量测试套件 |
| 无新增 lint 警告 | 运行 lint 检查 |
| 无未使用的代码 | 检查 dead code |
| 文档已更新 | 检查相关文档是否同步 |
| 无安全隐患 | 检查输入校验、权限控制 |

### 3. 回归检查

- 运行全量测试，确认无回归
- 检查变更是否影响了其他模块
- 检查是否有相关的集成测试需要更新

### 4. 生成验证报告

```markdown
## 验证报告

**变更：** [变更名称]
**日期：** [验证日期]

### 规格合规
- [x] 所有规格要求已实现
- [x] 所有边界情况已处理

### 质量验证
- [x] 全量测试通过（XX/XX）
- [x] 无新增 lint 警告
- [x] 无安全隐患

### 回归检查
- [x] 无功能回归
- [x] 相关模块测试通过

**结论：** 验证通过，可以标记为完成。
```

## Red Flags — 识别虚假完成的信号

| 想法 | 现实 |
|------|------|
| "代码能跑就是完成了" | 能跑不等于正确，正确不等于完整 |
| "主要功能做了就行" | 边界情况和错误处理也是功能的一部分 |
| "测试差不多通过了" | "差不多"不是通过 |
| "之后再补文档" | 文档是完成标准的一部分 |
| "这个警告一直都有" | 新警告和旧警告都需要关注 |

## Verification Checklist

- [ ] 是否已逐项对照规格确认合规？
- [ ] 是否已运行全量测试并全部通过？
- [ ] 是否已检查无新增 lint 警告？
- [ ] 是否已确认无安全隐患？
- [ ] 是否已生成验证报告？
