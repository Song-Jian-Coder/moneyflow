# Writing Plans — 实施计划编写

本技能将设计方案拆解为可执行的任务清单。每个任务粒度控制在 2-5 分钟，细到初级工程师也能直接执行。

## 核心原则

> 好的计划让执行变成例行公事。计划不是写给管理者看的，是写给执行者（包括未来的你自己和子代理）看的。

## Iron Law — 铁律

> **没有计划，不开始执行。计划中的每个任务必须可独立验证。**

## When to Use — 使用时机

- 设计方案已获批准（brainstorming 完成）
- 收到包含需求的多步骤任务说明
- 需要在编码前制定详细实施计划
- OpenSpec 的 `tasks.md` 需要编写或更新

## Process — 核心流程

### 1. 理解全貌

- 阅读设计方案 / 需求文档
- 识别所有需要变更的模块
- 理清模块间的依赖关系

### 2. 拆解任务

每个任务必须包含以下要素：

```markdown
### Task N: [任务名称]

**涉及文件：**
- `path/to/file1.ts` — 修改 XX 函数
- `path/to/file2.ts` — 新增 XX 接口

**具体操作：**
1. 在 file1.ts 中实现 XX 逻辑
2. 在 file2.ts 中定义 XX 接口
3. 编写单元测试覆盖 XX 场景

**验证方式：**
- [ ] 运行 `test_command`，所有测试通过
- [ ] 手动验证 XX 行为符合预期

**依赖：** 无 / 依赖 Task M
```

### 3. 排列顺序

- 按依赖关系排序（DAG）
- 无依赖的任务可以并行执行
- 高风险任务尽量前置（尽早暴露问题）

### 4. 审查计划

- 检查是否有遗漏的任务
- 检查每个任务的验证方式是否充分
- 检查任务粒度是否合适（2-5 分钟）

## 任务粒度指南

| 粒度 | 示例 | 判断 |
|------|------|------|
| 太大 | "实现用户认证系统" | 需要进一步拆解 |
| 合适 | "实现 JWT token 生成函数" | 2-5 分钟可完成 |
| 太小 | "导入 json 库" | 不需要单独成任务 |

## Red Flags — 识别不良计划的信号

| 想法 | 现实 |
|------|------|
| "这个任务很明显，不用写验证方式" | 没有验证方式的任务无法判断完成 |
| "把相关的小改动合并成一个大任务" | 合并后无法独立验证和回滚 |
| "先开始写，计划可以边做边补" | 边做边补的计划等于没有计划 |

## Verification Checklist

- [ ] 每个任务是否包含：涉及文件、具体操作、验证方式？
- [ ] 每个任务粒度是否在 2-5 分钟可完成？
- [ ] 任务间的依赖关系是否已标注？
- [ ] 是否有遗漏的模块或功能点？
- [ ] 计划是否可以被初级工程师独立执行？
